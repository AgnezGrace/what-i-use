# Platform adaptation

The foundation includes a universal workflow, not a verified list of platform-specific adapters. `index.json` is generated from reviewed adapter metadata. A known brand name is not evidence of current field names or model behavior.

For a requested destination: identify platform/version and actual creation fields. Use official documentation or a user-provided screenshot/field list. Record the source/date and distinguish observed UI from inferred runtime semantics. If neither is available, ask for the field list or give portable text labeled unmapped. Do not guess limits, macros, persistence, import support or field visibility.

Map canonical identity, motives, behavior, relationships, boundaries and voice into the verified durable fields; put scenario/state into the appropriate scene field, opening into greeting, and examples into examples only when supported. Public display fields must not receive private notes by accident. Never rely on a greeting alone to carry essential behavior when it is known not to persist. When persistence is unknown, say so.

Compress by retaining behavioral meaning, core canon, boundaries and context, then trimming redundant examples and decorative detail. Report any lost or relocated information. If a platform has one field, produce an integrated definition with labeled sections. Only produce a platform import file if its current specification is verified; a portable JSON profile is not a character card format.

Human users without Agent Skills support can use [universal-prompt.md](universal-prompt.md). For a future adapter, use the template in `../assets/adapter-template.md`; create its adapter metadata and run the synchronizer only after review. See [catalog maintenance](../core/catalog-maintenance.md). Reverify if the platform UI or docs change.
